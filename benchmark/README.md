# Бенчмарк Codex

Запускает один текст задания несколько раз в независимых сессиях Codex. Сохраняет токены, время, число ответов модели, ответы и результаты необязательных проверки задания и восстановления состояния.

Требуются Python 3.11+, Codex CLI в `PATH` с настроенной авторизацией и macOS/Linux. Внешние Python-пакеты не нужны. Формат внутренних логов проверен на локальном Codex CLI 0.153.4; при изменении формата часть метрик может стать недоступной.

## Запуск

Краткая инструкция для всех экспериментов: [testAgentRoots](../testAgentRoots/README.md).

Из корня проекта перейди в нужный agent root и укажи число повторов:

```bash
cd testAgentRoots/3_cli
bash ../run_benchmark.sh 5
```

Прямой вызов Python из той же папки: `python3 ../../benchmark/benchmark.py 5`. Единственный входной аргумент CLI — положительное целое число `iterations`; доступен также `--help`. Промпт и прежние флаги параметров больше не принимаются.

Все остальные параметры читаются из `benchmark_config.toml` в текущей папке. Пример для Jira-workflow:

```toml
prompt = 'Use $jira-start-task-cli for RC-80899'
cleanup_script = "../../benchmark/reset-jira-task.sh"
cleanup_args = ["RC-80899"]
validation_script = "../../benchmark/validate-jira-task.sh"
validation_args = ["RC-80899"]
```

`RC-80899` — тестовая задача; для другой задачи замени ключ и в `prompt`, в `cleanup_args` и `validation_args`. Промпт передаётся без shell-интерполяции и без изменения строки, прочитанной из TOML. Для многострочного текста можно использовать тройные одинарные кавычки TOML; перенос сразу после открывающих кавычек TOML отбрасывает.

| Поле TOML | Назначение / значение по умолчанию |
|---|---|
| `prompt` | Обязательный непустой текст задания |
| `model`, `profile` | Необязательные строки; при отсутствии настройки наследуются от Codex |
| `output_dir` | Родитель уникального каталога серии; по умолчанию `results/` рядом с `benchmark.py` |
| `timeout_seconds` | Положительный конечный числовой лимит эксперимента, 900 секунд |
| `cleanup_script` | Путь к исполняемому скрипту восстановления; при отсутствии cleanup отключён |
| `cleanup_args` | Массив строк, по умолчанию `[]`; непустой массив требует `cleanup_script` |
| `cleanup_timeout_seconds` | Положительный конечный числовой лимит cleanup, 120 секунд |
| `validation_script` | Путь к исполняемому скрипту проверки; при отсутствии проверка отключена |
| `validation_args` | Массив строк, по умолчанию `[]`; непустой массив требует `validation_script` |
| `validation_timeout_seconds` | Положительный конечный числовой лимит проверки, 120 секунд |

Неиспользуемые необязательные поля нужно опускать: значения `null` в TOML нет. Отсутствующий или повреждённый файл, неизвестные поля (включая `iterations`), неверные типы и неисполняемые скрипты cleanup/validation дают код `2` до запуска Codex и создания результатов. Эффективные параметры и число итераций сохраняются в `manifest.json`; массив `cleanup_args` сохраняет прежнее имя `cleanup_arg` в формате результатов.

Codex, validation и cleanup запускаются из текущей рабочей папки, в которой вызван бенчмарк. Этот путь записывается в `cwd` в `manifest.json` и `summary.json`. Относительные пути параметров разрешаются относительно той же папки; каталог результатов по умолчанию остаётся `benchmark/results/` рядом со скриптом. Модель, MCP и разрешения наследуются от Codex с учётом конфигурации выбранного agent root. Скрипт не отключает песочницу и не отвечает на вопросы агента: задание должно быть достаточным для неинтерактивного выполнения.

## Проверка результата через конфиг

`validation_script` запускается после успешного завершения процесса Codex, подтверждения `turn.completed` и чтения лога сессии, **перед cleanup**. Скрипт получает `validation_args` без shell-интерполяции, исходное окружение и `BENCHMARK_PHASE=validation`, `BENCHMARK_ITERATION` (номер повтора), `BENCHMARK_RUN_DIR` (абсолютный каталог повтора). Требуются исполняемый файл и shebang. Время проверки не входит во время эксперимента.

Код скрипта `0` означает успех. Ненулевой код, ошибка запуска или таймаут дают повтору статус `validation_failed`. Cleanup всё равно выполняется; следующие повторы продолжаются при успешном cleanup. Серия с неудачными проверками завершается с кодом `1`; такие повторы исключаются из средних и медиан, но их токены входят в общий расход. Ctrl+C во время проверки приводит к cleanup и завершению с кодом `130`.

При ошибке Codex, таймауте, прерывании или ошибке чтения/парсинга сессии проверка пропускается (`validation.status = skipped`). Без настройки используется `not_requested`. Результат проверки хранится отдельно в поле `validation`, включая статус, код выхода и длительность; исходный `exit_code` повтора остаётся кодом Codex. CSV содержит `validation_status` и `validation_seconds`.

## Cleanup

При N экспериментах выполняется N+1 вызов: один перед первым экспериментом и по одному после каждого, включая последний. Время cleanup не входит во время эксперимента. Без `cleanup_script` внешнее состояние не сбрасывается.

Cleanup запускается напрямую, без shell-интерполяции. Файл должен быть исполняемым и иметь shebang, например `#!/bin/bash` или `#!/usr/bin/env python3`.

Он получает переданные аргументы, окружение бенчмарка и дополнительные переменные:

| Переменная | Значение |
|---|---|
| `BENCHMARK_PHASE` | `setup` перед первым экспериментом, затем `cleanup` |
| `BENCHMARK_ITERATION` | `0` для подготовки, затем номер эксперимента от `1` |
| `BENCHMARK_RUN_DIR` | Абсолютный каталог серии для подготовки; каталог текущего повтора для cleanup |

Код `0` означает, что заданное состояние восстановлено и проверено. Скрипт должен допускать повторный запуск и частично выполненное задание. Для Jira он задаёт исходные статус и labels; история изменений остаётся.

Cleanup запускается также после ошибки и таймаута эксперимента. Ошибка cleanup останавливает всю серию. По таймауту и при Ctrl+C текущая группа процессов принудительно завершается через SIGKILL, затем бенчмарк пытается выполнить cleanup и сохраняет частичные результаты. Последние события принудительно завершённого процесса могут отсутствовать в логе. Принудительное уничтожение самого бенчмарка или выключение компьютера могут помешать восстановлению.

### Сброс Jira-задачи

[reset-jira-task.sh](reset-jira-task.sh) принимает один ключ задачи. Требуются Bash, `jq`, настроенный [jira-cli](https://github.com/ankitpokhrel/jira-cli) в `PATH` и доступ к серверу Jira. Самостоятельный запуск:

```bash
./benchmark/reset-jira-task.sh RC-80899
```

При `setup` и `cleanup` скрипт одинаково устанавливает `New` и удаляет только `ai_agent`, сохраняя остальные метки. Это фиксированное исходное состояние теста, а не восстановление произвольного исторического состояния: ранее существовавшая `ai_agent` тоже удаляется. История Jira сохраняется. Повторный запуск и частично выполненный workflow поддерживаются; промежуточные статусы скрипт не проходит.

После изменений скрипт повторно читает задачу и проверяет статус и набор меток. Код выхода `0` означает успешную проверку, `1` — ошибку CLI, некорректный ответ или несовпадение результата, `2` — неверные аргументы, `127` — отсутствие `jira` или `jq`. При ошибке выполнение останавливается; вывод CLI сохраняется в логах.

Общий таймаут обеспечивает бенчмарк (`cleanup_timeout_seconds`, по умолчанию 120 секунд); при самостоятельном запуске таймаута нет. Запуск неинтерактивный, дочерние процессы остаются в группе cleanup для внешнего завершения бенчмарком. Настройки Jira наследуются из окружения. `BENCHMARK_PHASE` и `BENCHMARK_ITERATION` добавляются в сообщение об успешной проверке; без них доступен самостоятельный запуск. От рабочего каталога и `BENCHMARK_RUN_DIR` скрипт не зависит. stdout/stderr сохраняет бенчмарк в своих cleanup-логах.

## Результаты и метрики

В уникальном каталоге серии находятся `manifest.json`, `summary.json`, `summary.csv` и каталоги `run-001`, `run-002`, … Стандартный каталог результатов исключён из Git.

Название каталога серии имеет формат `<UTC-время>-<случайный ID>-<имя папки запуска>`, например `20260927T155850Z-3d532695-1_mcp` при запуске из `testAgentRoots/1_mcp`.

Для каждого повтора сохраняются:

- `codex_output/events.jsonl` — исходный stdout `codex exec --json`;
- `codex_output/stderr.log`, `codex_output/final_answer.txt` — stderr и финальный ответ Codex;
- `codex_output/session.jsonl` — копия внутреннего лога, найденного по `thread_id`;
- `codex_output/trace-*/` — трейс Codex: `trace.jsonl`, `manifest.json` и `payloads/` с телами запросов и ответов, если установленная сборка поддерживает rollout trace;
- `benchmark_result.json` — результат и метрики бенчмарка;
- `validation/` — `stdout.log`, `stderr.log` и `result.json` выполненной проверки;
- `cleanup/` — отдельные логи и результат восстановления.

Файлы в `codex_output/` сохраняются побайтово, без переформатирования и исправлений. Далее имена этих файлов указаны относительно `codex_output/`.

Результаты повторов в `benchmark_result.json` и `summary.json` не содержат полей `command` и `directory`. Каталог повтора определяется по `iteration`: `run-001`, `run-002`, … Ранее сохранённые результаты не изменяются.

Для процесса Codex по умолчанию включён `RUST_LOG=warn,codex_api=trace`; диагностический вывод сохраняется в `stderr.log`. Если `RUST_LOG` уже задан в окружении, используется его значение. Фактический фильтр записывается в `codex_rust_log` в `manifest.json` и `summary.json`. Например, `RUST_LOG=warn python3 ../../benchmark/benchmark.py 1` из agent root отключает подробный trace. Cleanup получает исходное окружение бенчмарка.

В Codex CLI 0.153.4 при SSE-транспорте trace содержит исходные события с префиксом `SSE event:`, включая `response.completed`. По `response.id` можно сопоставлять их с `token_usage_record` и проверять наличие `usage`. Для WebSocket наличие такого полного журнала не гарантируется. Диагностический лог пока не участвует в автоматическом расчёте метрик. Подробное логирование добавляет затраты на запись, которые входят во время эксперимента.

Для каждого процесса Codex бенчмарк устанавливает `CODEX_ROLLOUT_TRACE_ROOT` в абсолютный путь его `run-xxx/codex_output`, переопределяя унаследованное значение. Codex создаёт внутри отдельную папку `trace-*`. В её `trace.jsonl` событие `inference_started` ссылается на тело запроса через `payload.request_payload.path`. Rollout trace не участвует в расчёте метрик; затраты на его запись входят во время эксперимента.

Время эксперимента измеряется монотонными часами от запуска процесса до его остановки. Включает запуск Codex, работу модели и инструментов; не включает последующий поиск/парсинг лога, validation и cleanup.

Токены берутся из `info.total_token_usage` последнего события `event_msg` с `payload.type: "token_count"` и непустым `info` в `session.jsonl`. Это накопленный расход сессии; `last_token_usage` не используется. Все поля, включая `total_tokens`, читаются напрямую, без суммирования. Входные токены уже включают кешированные, выходные — reasoning tokens. Отдельное поле `reasoning_output_tokens` не извлекается; исходные данные остаются в `session.jsonl`. Недоступные или некорректные числовые поля сохраняются как `null`; итоговая usage CLI не подставляется.

`model_responses` — количество записей с `type: "token_usage_record"` в `session.jsonl`, включая записи первого и финального ответов. Каждая запись учитывается независимо от наличия `response_id` и корректности `usage`; дубликаты тоже увеличивают счётчик. Если таких записей нет, значение — `0`. Повреждённые JSON-строки пропускаются с предупреждением. Это не число пользовательских turn и не число инструментов; запросы и сетевые повторы без такой записи не учитываются.

`events.jsonl` используется для получения `thread_id`, проверки завершения CLI и диагностики. Сырые события инструментов остаются в логах; отдельные счётчики вызовов и временной трейс не строятся.

Формат результатов — `schema_version: 1`. При упрощении бенчмарка удалены поля `models`, `tool_calls`, `mcp_calls`, `trace`, `trace_origin_ms`, `trace_origin_source` и файл `trace.jsonl`. События `turn_context` не обрабатываются. Также больше не сохраняются поля `reasoning_output_tokens`, `started_at_ms`, `usage_source` и промежуточный файл `process.json`. Ранее сохранённые результаты не изменяются.

Среднее и медиана считаются по завершённым экспериментам с доступной метрикой; рядом хранится число таких выборок. Общий зарегистрированный расход токенов включает неудачные попытки. Недоступные значения записываются как `null` в JSON и пустые ячейки CSV, в терминале — `N/A`. Статус `completed` подтверждает завершение процесса и turn, а при настроенной проверке — также её успех. Без `validation_script` смысловая правильность результата не проверяется.

Коды выхода: `0` — серия завершена без ошибок выполнения, `1` — ошибка эксперимента/validation/cleanup либо сбой парсера, `2` — неверные параметры, `130` — прерывание. Недоступные метрики отмечаются отдельно в `data_complete` и `warnings` и сами по себе не меняют успешный код выхода.

## Лог сессии

Лог сессии обязателен: после завершения процесса скрипт однократно ищет его по `thread_id` в `$CODEX_HOME/sessions` (по умолчанию `~/.codex/sessions`), однократно читает файл, сохраняет прочитанные байты в `codex_output/session.jsonl` и проверяет `session_meta`. Найденный и прочитанный лог сохраняется даже при пустом содержимом или неверных метаданных. Метрики вычисляются из тех же данных без повторного чтения. Время начала в `session_meta` не проверяется и не используется для измерения длительности. Ожидания появления или стабилизации файла нет. Отсутствующий или непригодный `thread_id`, отсутствие либо неоднозначность файла, ошибка чтения/копирования, пустой лог или неверные метаданные останавливают всю серию с кодом `1` и статусом `session_failed`. Причина сохраняется в `session_error` результата и выводится в консоль. Перед остановкой выполняется настроенный cleanup и сохраняется сводка; ошибка cleanup записывается отдельно. При Ctrl+C сохраняется код `130`.

Отсутствие отдельных метрик, неизвестные события и повреждённые строки после корректных метаданных не равнозначны отсутствию сессии: доступные данные сохраняются, проблемы чтения и метрик отмечаются в `warnings`. Время и метрики из CLI не подставляются. Обычная ошибка эксперимента при доступной сессии не препятствует следующим повторам, если cleanup успешен.

Cleanup имеет отдельные логи и не входит в метрики эксперимента. Новая сессия и cleanup не очищают серверный кеш. Проверка результата конкретного задания задаётся через `validation_script`; расчёт денежной стоимости в эту версию не входит.

## Проверка результата эксперимента 3

После выполнения workflow, **до сброса задачи**, запусти из корня репозитория:

```bash
bash benchmark/validate-jira-task.sh RC-80899
```

Скрипт требует настроенный `jira` и `jq` в `PATH`. Он только читает задачу и проверяет статус `Development` и наличие метки `ai_agent`; другие метки допустимы. Код выхода `0` — обе проверки прошли; ненулевой — проверка не пройдена или произошла ошибка выполнения.

Это проверка текущего состояния, а не истории переходов, сохранности прежних меток или выведенного описания. Во всех рутах эксперимента 3 (`3*`) скрипт подключён через `validation_script` и вызывается автоматически перед cleanup. При самостоятельном запуске после штатного cleanup ожидаемое состояние уже сброшено.

Источник публичного формата CLI: [официальная документация OpenAI](https://developers.openai.com/codex/noninteractive/#make-output-machine-readable). Внутренний формат `session.jsonl` отличается и не считается стабильным публичным API.
